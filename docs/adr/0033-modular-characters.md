# ADR-0033: Modular characters, generated then printed

- **Status:** Accepted
- **Date:** 2026-08-05
- **Deciders:** Nepomuk Crhonek
- **Approved-by:** Nepomuk Crhonek, 2026-08-05

## Context

A player was two initials on a coloured square. We wanted a character you build yourself — head, body,
arms, legs, twenty of each — which then becomes your profile picture everywhere in the game.

The binding constraint was that it **must not look AI-generated**, while the parts themselves are
generated by an image model. That tension is the whole problem, and it is worse than it sounds for a
modular system, because eighty separately generated images fail in four ways at once: the style
drifts, the scale wanders, the limbs do not line up with the bodies, and everything arrives with the
soft airbrushed shading that reads as machine-made.

## Decision

**The fix is not better prompting. It is collapsing the output space afterwards.**

Every part goes through one narrow pipeline — cut out, median filter, posterize to four flat inks,
hard key outline, halftone screen — and the narrowness is the point. Two parts that look unrelated in
full colour look like siblings once both are four flat inks with the same screen over them.

The numbers from the pilot, measured rather than estimated:

| | before | after |
| --- | --- | --- |
| distinct opaque colours in one head | 16,744 | 8 |
| pixels with partial alpha | 9.3% | 0% |

That first row is the important one. The model's output *looks* flat and is not; it dithers
imperceptibly, and that dither is different in every image. Posterizing to the Overprint inks
(ADR-0032) destroys it. The halftone does the rest — a regular dot screen is a print artefact no
image model produces on its own, so adding a real one is a signal in the opposite direction.

### Generation

`gpt-image-1`, not `gpt-image-2`, despite the latter being newer. `gpt-image-2` cannot return a
transparent background at all — it rejects the parameter — and when asked for a flat magenta field to
key out, it returned a hot pink instead. That is a background-colour lottery on every one of eighty
calls. `gpt-image-1`'s native alpha is simply better suited.

Three things about the API that shaped the scripts:

- **Roughly one call in four returns HTTP 520** from the edge, as an HTML error page rather than
  JSON. Transient, and retries clear it, but without them parts silently go missing.
- **Responses are 1.5 MB of base64 and `urllib` truncates them** — `IncompleteRead(409600 bytes read,
  1636233 more expected)`. Everything goes through `curl --retry` instead, which just works.
- **Rate limits bite at about three concurrent.**

So `generate_all.py` is **resumable**: anything already on disk is skipped, and the fix for a partial
run is to run it again.

Prompts are also shaped by two findings. Limb prompts are framed as **paper-puppet pieces** rather
than detached body parts — "a single detached arm" reads as dismemberment and trips the safety
filter. And the torso is asked for as **a vest laid flat with nothing inside it**, because "a torso
with no arms" comes back with arms every time: the model draws the person it pictures and removes
nothing.

### The rig

Alignment is not asked of the model. `rig.json` fixes five points — neck, both shoulders, both hips —
and each part records the pivot it hangs from, measured off the finished artwork by the generator.

**The pivot is not the same edge for every slot.** A limb swings from its top, so its pivot is
top-centre. A head turns about the *neck*, which is at the bottom of the drawing. Getting that
backwards is not subtle: a head pivoted at its crown swings like a pendulum instead of turning to
look at you.

**`neck` and `chin` are two points, thirty pixels apart.** The torso hangs from `neck` and the head
from `chin`, so the head overlaps the torso rather than resting on it. Level with each other they
merely abut — and since the vest has an open neck hole, the page background shows through the join
and the head reads as detached. The head is drawn after the body, so it covers the seam.

**No part may have a handedness.** The far limb is the near limb mirrored, so a gesture that means
something specific comes out reversed on one side. The catalogue originally held a palm-forward V
sign; mirrored it became the back of the hand, which is a rude gesture across much of Europe. It is
now an open waving hand, which reads the same either way round.

Limbs are drawn straight and vertical, and each is one drawing used twice — the second mirrored. That
halves the catalogue and guarantees the two sides match.

### Animation

Six layers, CSS transforms, GPU-composited. Legs counter-rotate, arms counter-swing, the torso bobs,
all on deliberately mismatched periods so the loop never lands on itself and start reading as a
mechanism. The head follows the pointer, clamped to ±12°, written straight to the node through a ref
rather than through React state — otherwise every mouse move re-renders the whole figure.

One structural detail worth knowing: **the mirror and the rotation are on different elements.** A CSS
animation overrides an inline style, so a `scaleX(-1)` written alongside the rotation would vanish the
moment a limb started swinging. The flip therefore lives on an inner image, and the far side runs the
same keyframes with `animation-direction: reverse` — which is what makes it a walk rather than a
march.

### Wearing it, with no interface change

The composed still is uploaded to Clerk with `setProfileImage()`. `profile.service.ts` already caches
`identity.imageUrl`, so friend lists, chat, the leaderboard, notifications and Clerk's own account
menu all show the character **without any of them being told characters exist**. The part ids go in
`unsafeMetadata` so the picker can be reopened.

In local development there is no Clerk, so the picture is inlined as a data URL into the same
`imageUrl` field. Both paths end identically, and `<Avatar>` never learns the difference.

**Nothing in `packages/shared` or `apps/backend` changes.** No interface ADR, no team agreement, no
DynamoDB migration.

The square is a **portrait**: the head, centred, with just enough shoulder beneath it to sit on. An
avatar renders at 32 pixels in a friend list, and a full standing figure at that size is an
unreadable smudge — the head alone would be about nine pixels across. The 260-pixel window is sized
against the artwork rather than by eye: the widest head is 218 and every head is 190 tall, so the
largest of them fits with margin.

### Everybody builds one

The gate reads what is *stored*, not when the account was created, so players who registered before
this existed meet the same screen. No backfill script, no migration, no second code path.

**It is a UX gate, not a security boundary** — it runs in the browser and reads client-writable
metadata. That is the correct standing for something purely cosmetic, and the same standing CLAUDE.md
already gives the frontend room guard. Making it server-enforced would mean a `needsCharacter` flag on
the API, which means `packages/shared`, which means an interface ADR and team agreement.

### The picker

It **opens on a complete random character**, never an empty outline. Changing the bits you dislike is
a far easier question than assembling a person from nothing, and anyone who does not care can press
straight on. One slot at a time — twenty thumbnails is a glanceable grid, eighty is a wall — with
arrows beside the figure so the current slot can be cycled without looking away from the character,
and arrow keys doing the same because the grid is a radio group.

**The whole catalogue is preloaded when the picker mounts.** Otherwise the first click on a
thumbnail fetches that part's full-size image and the figure changes a beat *after* the click, which
reads as the app being slow rather than as an image loading. The catalogue is under a megabyte, so
the honest fix is to have all of it before it is wanted rather than to make the delay prettier.

**It can be reopened.** "Change character" in the game header returns to the picker, starting from
who you already are and with a way to back out — neither of which is true of the sign-up gate, where
there is nothing behind the screen to go back to.

## Consequences

**Good**

- It does not look generated, which was the requirement, and the reason is mechanical rather than a
  matter of taste.
- Adding parts is a line in `parts.py` and a rerun. Removing one is a line and a rerun.
- 160,000 combinations from 80 files, about 700 KB total, served as static assets. No new
  infrastructure.
- Nothing downstream of the profile picture had to change.

**Bad**

- **The catalogue is generated art and it will not be uniformly good.** Some of eighty parts will be
  weak. The `Character.test.tsx` completeness check catches a *missing* part, not an ugly one; that
  needs eyes on a contact sheet.
- **Regenerating a part changes its pivot and size**, because both are measured from the artwork. The
  manifest is regenerated with it, so this is handled — but the manifest must never be edited by hand.
- **`unsafeMetadata` is client-writable**, so a determined player can give themselves a character the
  picker would not offer. It is cosmetic; the cost of preventing it is an interface change.
- **The composed data URL in local development is a few hundred KB in localStorage**, which is where a
  quota error would surface first.
- Eighty images cost a few dollars and about forty minutes wall-clock, most of it retries.

**Notable**

- `gpt-image-2` exists on the key and is the wrong tool for this. Recorded so nobody "upgrades" to it.
- The scripts need `OPENAI_API_KEY` in the environment. It is never written into the repo.

## Alternatives considered

**Procedural SVG parts.** Perfectly registered, a few kilobytes total, infinitely scalable, and
certainly not machine-made. Rejected because eighty hand-authored parts is more work than eighty
generated ones and less varied — but this remains the fallback if the catalogue disappoints, and the
rig would not change.

**Full colour rather than two inks.** More striking, and far harder to keep consistent: full colour is
exactly where style drift is visible and where generated images look generated.

**Storing the character in our own profile and enforcing the gate server-side.** Architecturally
consistent with how `needsProfile` works, and it would make the gate real rather than cosmetic.
Rejected for now because it means `packages/shared`, an interface ADR and prior team agreement, for a
feature that decides what a face looks like.

**Compositing the four parts live everywhere instead of uploading a still.** Would keep the character
animated in friend lists. Rejected: twenty idling figures in a list is unbearable, at 32 pixels the
motion is invisible, and it would mean every avatar surface in the app learning what a character is.
