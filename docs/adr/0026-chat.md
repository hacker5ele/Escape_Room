# ADR-0026: One-to-one chat between friends

- **Status:** Accepted
- **Date:** 2026-08-04
- **Deciders:** Nepomuk Crhonek

## Context

Friends exist and notifications work, so people can find each other and be told when something
happens. Chat is the thing they actually want to do with that.

It is also, by a wide margin, the most dangerous feature in this project. Everything else here leaks
at worst a username. Chat holds things people said in private, and the rival team gets the app on
Thursday.

## Decision

### The conversation id is derived, never accepted

`conversationIdFor(a, b)` sorts the two user ids and joins them. Both sides compute the same value
without having to agree on one in advance.

Crucially, **no URL, body or query parameter anywhere in the chat API contains a conversation id.**
Endpoints are addressed by *person*: `GET /api/chat/:userId/messages`. The server combines the
caller's authenticated id with the friend they named, and there is simply no request shape in which
somebody can ask for a conversation they are not part of. Mallory asking for Alice's messages gets
the Mallory-and-Alice conversation, which is empty and which she is entitled to.

If a client could supply this value, it could read anybody's messages. That is the single line this
ADR exists to protect.

### Friendship is checked on every read and every write

Not once when the conversation opens. Checking at open time would leave an already-open tab working
indefinitely after the friendship ended — and "indefinitely" includes after a block.

Both a `403 NOT_FRIENDS` for strangers, for people with only a pending request, for people who have
been unfriended, and for people who have been blocked. One error covers all of them, so the endpoint
cannot be used to work out which.

A friend request does **not** open a channel. Only an accepted, mutual friendship does.

### Messages are stored exactly as typed, and escaped at render

Nothing is escaped on the way in. Escaping at write time double-escapes at read time, and it means
the stored data is in a format that depends on how it happens to be displayed. React escapes at
render, and `dangerouslySetInnerHTML` does not appear anywhere near a message.

Length is capped at 2000 characters. Not for storage cost — a message is stored once and then
returned on every poll to everybody in the conversation, so an unbounded field is a way to make
somebody else's every future request expensive.

### One bell notification per conversation, not per message

Before writing a "you have a new message" notification, the service checks whether the recipient
already has an unread one from the same person. Somebody typing five lines in a row rings the bell
once. Once they have read it, the next message rings again.

Without this, chat makes the notification system useless within a day.

### An open conversation polls faster than the bell

Three seconds versus ten. Ten is unnoticeable for "somebody added you" and unusable for a
conversation where the other person is watching the screen. It stops when the tab is hidden, like
every other poll here.

A sent message is folded into the view immediately rather than waiting for the next poll to return
something the client already has.

### No TTL on messages

Unlike notifications, a conversation is content people expect to still be there tomorrow. The table
grows; at this scale that is irrelevant.

## Consequences

**Good**

- There is no request that names another pair's conversation, so the dangerous case is structurally
  impossible rather than defended against.
- Blocking closes the conversation immediately, including for an open tab.
- Reading a conversation is a single Query.

**Bad**

- Up to three seconds of latency. Acceptable; the alternative needs a platform that supports
  WebSockets (see ADR-0025).
- No paging beyond the most recent 100 messages. Fine for a build this size, and a straightforward
  addition later — the sort key already supports it.
- No delivered or read receipts, no typing indicator, no editing or deleting. Deliberately out of
  scope.

**Notable**

- The sort key is `${createdAt}#${id}`, the same scheme as notifications, now shared in
  `repositories/sort-key.ts`.

## Alternatives considered

**A conversations table with generated ids.** The usual design, and it needs a membership check on
every request *and* a way to resolve a conversation from a pair. Deriving the id makes the membership
check the only thing to get right, and there is nothing to look up.

**Group chat.** Would require the conversations table above, since a set of members no longer derives
from two ids. Not asked for, and not worth the extra surface this week.

**Encrypting messages at rest beyond DynamoDB's default.** Key management would be the hard part, the
server has to read messages to serve them anyway, and it would protect against a threat — someone with
AWS console access — who already has more direct routes. Not worth it here.
